# Disaster Recovery & Encrypted Backup Runbook

This runbook documents the ADAS Globus CRM backup architecture, off-site replication, key custody, monthly restore drills, and bare-metal disaster recovery (`PRD §10.5`, `ADR 0025`).

- **Recovery Point Objective (RPO):** `<= 15 minutes` (with continuous WAL archiving + scheduled encrypted `pg_dump -Fc` snapshots)
- **Recovery Time Objective (RTO):** `<= 4 hours` (full bare-metal Ubuntu LTS rebuild + off-site restore)

---

## 1. Backup Envelope & Off-Site Replication Architecture

### `ADASBK01` Encrypted Archive Format

Every snapshot generated by `BackupManager` (`apps/api/src/platform/backup/index.ts`) runs `pg_dump -Fc --no-owner --no-privileges` against PostgreSQL 17 and encrypts the binary dump client-side before touching disk or S3:

| Offset   | Length     | Field                                                      |
| -------- | ---------- | ---------------------------------------------------------- |
| `0..7`   | `8 bytes`  | ASCII magic header `ADASBK01`                              |
| `8..19`  | `12 bytes` | Cryptographic random AES-GCM IV (`randomBytes(12)`)        |
| `20..35` | `16 bytes` | AES-256-GCM authentication tag (AAD bound to `'ADASBK01'`) |
| `36..N`  | Variable   | AES-256-GCM ciphertext of the `pg_dump -Fc` archive        |

- **Encryption Key Custody (`Q7`):** Derived via SHA-256 from `secrets/backup_encryption_key.txt`. Two named key holders must store offline copies of `backup_encryption_key.txt` and `token_encryption_key.txt` in separate company password vaults outside the office server! Without `backup_encryption_key.txt`, off-site `.adasbk` archives cannot be decrypted; without `token_encryption_key.txt`, encrypted OAuth/TOTP/webhook secrets must be re-connected after restore.
- **Off-Site Replication (`S3SigV4Client`):** Zero-dependency AWS Signature v4 client uploads every `.adasbk` archive over HTTPS (`PUT` with `x-amz-content-sha256`) to Cloudflare R2, Backblaze B2, or Amazon S3 (`BACKUP_S3_ENDPOINT`, `BACKUP_S3_BUCKET`).
- **Retention:** Local and telemetry-tracked archives older than `BACKUP_RETENTION_DAYS` (`14` days default) are pruned automatically after successful backups.
- **Monitoring:** Every backup and restore drill writes to `backup_runs` (surfaced on `GET /healthz` and `Settings → System health`) and optionally pings `UPTIME_KUMA_PUSH_URL`. `/healthz` reports `degraded` if the latest successful backup is older than `26` hours.

## 2. Manual On-Demand Backup

From the server host:

```bash
docker compose -f /opt/adas-crm/infra/compose.prod.yml run --rm --no-deps api \
  node --conditions=production-dist apps/api/dist/cli/backup.js backup --kind=manual
```

_(Or click **Run encrypted backup** in the Electron Server Management Console -> **Backups & recovery**.)_

## 3. Monthly Automated Restore Drill (`scripts/restore-drill.sh` — `PRD §12.1 A21`)

Run on the 1st business day of every month (and **before** first production go-live):

```bash
bash /opt/adas-crm/scripts/restore-drill.sh
```

What the drill proves without touching production traffic:

1. Locates the newest `.adasbk` archive (downloading from off-site S3/R2 if `--from-s3` is passed).
2. Verifies the `ADASBK01` header and AES-256-GCM authentication tag, decrypting in a `0700` temp directory.
3. Creates a disposable database `adas_restore_drill_<timestamp>`, runs `pg_restore`, and verifies:
   - Core table accessibility (`users`, `companies`, `contacts`, `leads`, `deals`, `activities`, `audit_logs`, `suppressions`),
   - Schema-qualified `public.immutable_unaccent` full-text `search_tsv` GIN indexes (`ADR 0024`),
   - Foreign-key consistency (`0` orphaned contacts), and
   - Append-only immutability triggers (`UPDATE/DELETE` on `audit_logs` and `DELETE` on `suppressions` are rejected!).
4. Drops the disposable database, records `kind = 'restore_drill', status = 'succeeded'` in `backup_runs`, and notifies Uptime Kuma.

## 4. Full Bare-Metal Disaster Recovery Procedure

If the office server SSD fails or the machine is replaced:

1. **Provision replacement Ubuntu Server LTS host:**
   ```bash
   git clone https://github.com/Destroyerved/adas-globus-crm.git /opt/adas-crm
   /opt/adas-crm/installer/install.sh provision --install-docker --domain adasglobuspro.com
   ```
2. **Restore escrowed keys into `/opt/adas-crm/secrets/` (`chmod 600`):**
   - Overwrite `secrets/backup_encryption_key.txt` and `secrets/token_encryption_key.txt` with the escrowed production keys from the company vault!
3. **Download latest `.adasbk` archive from Cloudflare R2 / Backblaze B2** into `/opt/adas-crm/data/backups/`.
4. **Start PostgreSQL 17 and restore the encrypted archive:**
   ```bash
   cd /opt/adas-crm
   docker build -f infra/Dockerfile.api -t adas-crm-api:v1.0.0 .
   docker compose -f infra/compose.prod.yml up -d postgres
   docker compose -f infra/compose.prod.yml run --rm --no-deps api \
     node --conditions=production-dist apps/api/dist/cli/backup.js restore \
     --file=/app/data/backups/<latest-archive>.adasbk \
     --confirm=RESTORE_PRODUCTION_DATABASE
   ```
5. **Re-apply forward migrations (if restoring onto a newer code tag) and start all services:**
   ```bash
   docker compose -f infra/compose.prod.yml run --rm --no-deps api \
     node --conditions=production-dist apps/api/dist/cli/migrate.js
   docker compose -f infra/compose.prod.yml up -d api worker backup uptime-kuma cloudflared
   curl -fsS "http://127.0.0.1:3000/healthz?strict=1"
   ```
6. **Verify post-restore integrity:** Sign in via Entra SSO (or Break-Glass Admin), confirm `Settings → System health` shows `Healthy` across PostgreSQL, workers, and outbox, and confirm `Settings → Audit log` shows unbroken historical records.
